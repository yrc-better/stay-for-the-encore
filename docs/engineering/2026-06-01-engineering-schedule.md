# 乐队模拟器工程排期（沙盒事件版）

## 目的

这份文档把《乐队模拟器》从当前可玩 MVP 推进到可发布网页版本。项目定位调整为沙盒经营模拟：随机事件是主要体验，固定剧情只承担关键人生节点、阶段锚点和保底引导。

排期按“可验收、可回滚、可试玩”的工程阶段组织。V1 先完成“校园序章 + 毕业后第一年”的沙盒纵切，同时建立可扩展到后续年份的事件池、年度结算和生涯阶段框架。

## 检查结论

截至 2026-06-01，代码基线稳定，但排期需要从“功能清单”优化为“沙盒事件系统 + 阶段门禁 + 内容产能控制”。

已验证基线：

- 测试：`vitest run` 通过，10 个测试文件、70 个测试全部通过。
- 类型检查：`tsc --noEmit` 通过。
- 构建：`vite build` 通过，生产包可生成。
- 说明：当前 shell 没有直接暴露 `npm`，验证使用本地 `node_modules/.bin/*` 和 Codex 工作区 Node 运行时完成。

主要发现：

- 当前 MVP 已有行动、事件、反馈、履历、存档校验、响应式界面和结局评估模块。
- 当前事件系统按触发条件和优先级返回可用事件，实际体验偏固定顺序；需要升级为权重抽取、冷却、保底和稀有事件机制。
- `Release` 数据类型已存在，但 `Recording -> Release` 的正式发行路径还没有落到玩家流程。
- `record` 行动当前更像占位行动，没有真正调用录音生产规则。
- 存档是版本号 + 形状校验，没有 schema migration；新增 `phase`、`careerStage`、事件历史、成员实体或发行字段前必须先补迁移。
- 后续最大风险不是框架搭建，而是随机事件池、特殊剧情、成员线和长期年份内容的生产与校验。
- 原排期中“第一版只做第一年”和“寿命终局”之间存在范围张力，优化后 V1 做第一年内容和长期框架，V2+ 逐步扩展后续年份事件池。

## 发布范围

V1 发布必须包含：

- 从开局到校园毕业演出的完整序章。
- 毕业后第一年 12 个月的主循环。
- 随机事件抽取器：权重、冷却、稀有度、一次性事件、保底事件。
- 固定剧情锚点：毕业演出、第一次关键演出机会、第一次 Demo 或发行结果、首次重大成员冲突。
- 至少一次自然 Demo 生产、一次演出机会、一次发行或投递结果。
- 成员关系能够产生实际后果，至少覆盖冲突、缓和、离队风险。
- 本地存档具备迁移能力，坏档不会白屏。
- 手机和桌面都能完整游玩 30 分钟以上。

V1 不包含：

- 后续所有年份的完整事件内容。
- 大规模巡演、完整唱片工业模拟、在线账号、云存档、排行榜。
- 节奏按键演奏、3D 场景或复杂动画系统。

V1 必须预留：

- `careerStage` 或等价字段，用于区分起步期、上升期、成熟期、后期生涯。
- 年度结算入口，用于把长期年份从逐月内容压力中解放出来。
- 事件池分层结构，允许后续按年份、阶段、名声、健康、成员状态、作品成绩继续扩展。

## 排期原则

- 沙盒优先：普通月体验由随机事件池驱动，固定剧情只做锚点和保底。
- 每个阶段结束都必须保持网页可运行、测试通过、可本地试玩。
- 先做事件机制，再扩内容量；每次内容扩充都配内容校验测试。
- 状态结构先迁移后扩展，避免旧存档直接失效。
- 每个阶段设置“范围冻结线”，冻结后只修验收问题，不追加新系统。
- 第一版以第一年沙盒纵切为准，后续版本按生涯阶段扩展长期生涯。

## 关键依赖顺序

1. 存档迁移能力先于新增核心状态字段。
2. `phase: "campus" | "career"` 先于校园和毕业后事件分流。
3. `careerStage` 先于后续年份事件池。
4. 随机事件抽取器先于大规模事件生产。
5. 内容校验测试先于大规模扩事件。
6. `Recording -> Release` 规则先于发行、销量、奖项、结局读取。
7. 成员实体先于离队、新人加入、成员支线。
8. 年度结算先于第 2 年以后长期生涯扩展。
9. 结局解释页先于公开发布，避免称号只像调试结果。

## 沙盒事件系统设计

### 事件类型

随机事件是常规体验，固定剧情是锚点。

| 类型 | 用途 | 例子 | 触发方式 |
| --- | --- | --- | --- |
| 普通随机事件 | 形成每月差异 | 练习瓶颈、设备故障、临时邀演、灵感片段、成员小摩擦 | 权重抽取，可重复或冷却 |
| 出身路线随机事件 | 强化出身路线差异 | 技术宅的设备研究、创作型的编曲争执、舞台型的现场机会、叛逆型的商业冲突 | route + 阶段 + 权重 |
| 成员随机事件 | 让关系长期波动 | 主唱失眠、贝斯沉默抗议、鼓手排练迟到 | 成员状态 + 关系 + 冷却 |
| 机会随机事件 | 提供沙盒目标 | Livehouse、录音室折扣、厂牌邮件、乐评人关注 | 名声、作品、资金、口碑权重 |
| 风险随机事件 | 制造代价 | 透支、健康下滑、错过工作、合约陷阱 | 压力、健康、资金、关系权重 |
| 稀有特殊事件 | 形成传记感 | 极端现场、成员摊牌、地下爆红、创作爆发、健康危机 | 低概率 + 严格条件 |
| 固定剧情锚点 | 保证结构成立 | 毕业演出、第一次关键演出、第一次发行、终局入口 | 条件满足或保底触发 |

### 抽取规则

每月事件流程建议：

1. 月初更新阶段、状态、冷却和年度计数。
2. 收集符合条件的随机事件候选。
3. 按权重、稀有度、近期重复惩罚、玩家路线加成计算最终权重。
4. 抽取 0 至 2 个本月事件，关键月允许追加固定锚点。
5. 如果关键体验长期未发生，触发保底事件。
6. 事件结果写入履历、flags、冷却、成员状态或后续事件队列。

事件字段需要扩展：

- `category`: `random`、`anchor`、`rare`、`fallback`。
- `phase`: `campus`、`career` 或两者兼容。
- `careerStages`: 起步期、上升期、成熟期、后期生涯。
- `rarity`: 普通、少见、稀有、传说。
- `weight`: 基础权重。
- `cooldownMonths`: 触发后冷却。
- `repeatable`: 是否可重复。
- `maxPerYear`: 年度最多触发次数。
- `fallbackAfterMonths`: 多久未发生同类体验后保底。
- `blocksTags` / `requiresTags`: 控制互斥和前置。

### 固定剧情锚点

固定剧情不应该抢走沙盒感，只负责让人生结构不散。

V1 固定锚点：

- 毕业演出：校园序章收束，读取排练、作品、关系、压力。
- 第一次关键演出机会：如果随机演出长期未出现，用低级机会保底。
- 第一次 Demo 或发行结果：如果玩家已有作品但没有结果，用投递或小范围发布保底。
- 第一次重大成员冲突：关系长期低或压力高时出现，不应无条件强制。
- 结局入口：退役、解散、健康崩溃、告别演出或测试态触发。

特殊固定剧情可以是条件触发，不是必定发生。例如高名声 + 高压力可能触发大型演出事故；低关系 + 高作品质量可能触发创作权摊牌；地下口碑极高但财富低可能触发厂牌诱惑。

### 后续年份推进方式

后续年份不逐月手写主线，而是按生涯阶段解锁事件池。

| 生涯阶段 | 年份范围 | 核心体验 | 主要事件池 |
| --- | --- | --- | --- |
| 校园序章 | 毕业前 | 组队、毕业演出、第一次选择代价 | 校园、职业、成员关系、毕业演出 |
| 起步期 | 第 1-3 年 | 找机会、做 Demo、小演出、穷和累 | Livehouse、兼职、录音室、地下口碑、小厂牌 |
| 上升期 / 困住期 | 第 4-7 年 | 是继续地下还是走商业，是成长还是原地打转 | 首张专辑、合约、巡演、风格转型、成员裂痕 |
| 成熟期 / 危机期 | 第 8-15 年 | 名声、商业压力、身体代价、成员命运 | 大巡演、口碑反噬、制作人合作、离队复归、健康风险 |
| 后期生涯 | 第 15 年以后 | 退役、复出、转型、人生评价 | 告别演出、重组、转制作人、经典巡演、终局评价 |

年度结算负责处理长期变化：

- 年度作品成绩。
- 年度演出次数和疲劳。
- 名声、粉丝、财富和口碑趋势。
- 成员关系和成员状态变化。
- 健康、压力、透支债务。
- 解锁下一生涯阶段或终局入口。

## 阶段 0：MVP 收口

**时间：2026-06-01 至 2026-06-03**

目标是把当前 MVP 整理成可继续开发的稳定基线。

必须交付：

- 移除或隐藏调试性质的结局入口，保留规则层和测试。
- 梳理当前 UI、规则、内容、存档模块的文档索引。
- 确认所有行动、事件选项、下月推进、重开都有明确反馈或可感知状态变化。
- 增加坏档恢复场景测试，确保 localStorage 损坏时回到开局而不是白屏。
- 记录当前系统缺口：阶段状态、随机事件抽取器、录音行动、发行路径、存档迁移。

验收标准：

- `vitest run`、`tsc --noEmit`、`vite build` 全部通过。
- 手机和桌面都能完成开局、行动、事件选择、进入下个月、重开。
- 坏存档、空存档、旧结构存档都有明确行为。

范围冻结线：

- 不新增大剧情线。
- 不新增长期生涯内容。

## 阶段 1：校园随机事件 + 毕业演出锚点

**时间：2026-06-04 至 2026-06-14**

目标是把毕业演出前一个月做成沙盒序章，并验证随机事件、出身路线差异、成员关系、毕业演出和履历链路。

必须交付：

- 新增 `phase` 状态和存档迁移。
- 实现最小随机事件抽取器：权重、once、repeatable、冷却、随机种子或可测试随机源。
- 校园序章按上旬、下旬、毕业演出三个节点推进，但普通体验由校园随机事件池提供。
- 毕业演出作为固定锚点，读取排练、关系、作品质量、压力、体力透支。
- 序章结果写入履历，并影响毕业后开局资源。
- 内容校验测试：事件 id 唯一、触发条件有效、选项可达、反馈存在、权重有效。

内容目标：

- 校园普通随机事件：10 至 12 个。
- 出身路线随机事件：12 个，四条出身路线各 3 个。
- 成员随机事件：6 至 9 个。
- 稀有校园特殊事件：3 至 4 个。
- 毕业演出固定结果：4 至 6 种。

验收标准：

- 从新开局到毕业演出至少需要 15 分钟。
- 同一出身路线连续开两局能看到不同事件组合。
- 四条出身路线能看到不同事件或不同选项。
- 毕业演出结果能明显反映玩家前期操作。
- 序章结束后进入 `career` 阶段，不依赖硬编码月份判断。

范围冻结线：

- 只做固定四人乐队。
- 校园阶段不引入唱片公司、巡演和新人加入。

## 阶段 2：毕业后第一年随机机会循环

**时间：2026-06-15 至 2026-06-30**

目标是完成“毕业后才是主线”的第一年沙盒纵切，让玩家能看到随机机会、代价、保底和长期反馈。

必须交付：

- 毕业后 12 个月节奏配置，区分月初机会、行动反馈、月末结算。
- 扩展随机事件抽取器：稀有度、年度上限、重复惩罚、保底触发。
- Livehouse、地下场景、录音室、唱片合作等机会随机事件。
- Demo 录制后的投递、发布或错过机会流程。
- 粉丝、口碑、资金、关系的长期反馈。
- 成员离队风险和新人加入的前置事件，不要求完整阵容系统在本阶段完成。

内容目标：

- 毕业后普通随机事件：20 至 25 个。
- Livehouse / 演出随机事件：8 至 10 个。
- Demo / 录音 / 合作随机事件：8 至 10 个。
- 成员风险随机事件：6 至 8 个。
- 第一年稀有特殊事件：4 至 6 个。
- 第一年固定保底锚点：2 至 3 个。

验收标准：

- 毕业后 12 个月内至少能自然完成一次 Demo 和一次演出；如果随机长期不给机会，保底事件必须介入。
- 连续两局第一年事件顺序和组合不同。
- 玩家能看到销量、荣誉、合约或人脉作为成果事件出现。
- 成员关系差异能触发实质后果，而不只是显示数值变化。
- 第一年的低投入、高透支、关系破裂路线都能跑通到明确结果。

范围冻结线：

- 不做完整专辑周期。
- 不做第 2 年以后内容池，但要保留 `careerStage` 或等价扩展点。

## 阶段 3：作品、录音和发行闭环

**时间：2026-07-01 至 2026-07-14**

目标是让“创作、排练、录音、发行、评价”形成可复用闭环，并让事件池能读取作品成果。

必须交付：

- 将 `record` 行动接入正式录音规则，满足作品完成度和排练门槛时生成 `Recording`。
- 实现 `Recording -> Release` 的正式生产路径。
- 支持 Demo、单曲、EP、专辑的最小发布规则；V1 至少自然支持 Demo 和单曲。
- 销量、专业评价、地下口碑、粉丝增长公式。
- 作品风格标签聚合，并影响随机事件权重、履历和结局称号。
- 履历页展示关键作品、录音和发行成果。

验收标准：

- 玩家可以从 Riff 推进到至少一种 Release。
- 发行结果不是固定值，而是受作品质量、排练、装备、名声、宣传影响。
- 发行结果能改变后续随机事件权重，例如更多演出、合作、乐评或商业压力。
- 成果数据能被后续结局称号读取。
- 录音或发行条件不足时，UI 给出明确原因。

范围冻结线：

- EP 和专辑可以先共用规则，不做复杂制作周期。
- 不引入外部曲库、授权音乐或真实乐队引用。

## 阶段 4：成员剧情和乐队风险

**时间：2026-07-15 至 2026-07-31**

目标是把乐队从数值面板推进到有成员命运的群像模拟，并让成员状态参与随机事件权重。

必须交付：

- 固定成员的人物档案、性格倾向、能力字段和压力字段。
- 主唱、贝斯、鼓手的个人随机事件池和少量特殊剧情。
- 创作权冲突、主导权冲突、巡演压力、商业妥协事件。
- 离队、暂别、复归、新人加入的最小状态变化。
- 成员关系对排练、演出、录音、事件权重的实质影响。

验收标准：

- 至少一个成员可以因长期关系和事件选择进入离队或暂别状态。
- 至少一个新人加入事件能改变乐队能力结构。
- 成员剧情必须影响数值、履历、后续事件或作品结果。
- 成员状态在 UI 上可读，不需要玩家猜测隐藏后果。
- 成员低关系、高压力、高名声三类状态能触发不同事件倾向。

范围冻结线：

- 不做大规模可招募角色池。
- 不做复杂角色养成装备。

## 阶段 5：结局入口和长期生涯框架

**时间：2026-08-01 至 2026-08-14**

目标是把结局页从规则模块变成正式游戏体验，同时建立第 2 年以后的可扩展框架。

必须交付：

- 正式结局入口：退役、告别演出、乐队解散、健康崩溃或测试态触发。
- 职业称号判定读取作品、发行、演出、关系、健康、压力、荣誉。
- 结局页解释关键判定依据。
- 结局履历摘要：荣耀、遗憾、关键作品、关键成员关系。
- `careerStage` 或等价长期阶段字段：起步期、上升期、成熟期、后期生涯。
- 年度结算雏形：作品成绩、演出次数、疲劳、成员关系、健康债务、名声趋势。
- 至少 8 个职业称号可通过测试态稳定触发。

验收标准：

- 结局不只显示标题，必须解释为什么得到这个人生评价。
- 不同路线至少能触发 4 种明显不同的结局体验。
- 结局页不提前泄露称号倾向，只在终局展示。
- 第 2 年以后即使内容很少，也能通过年度结算和事件池框架继续推进而不崩坏。

范围冻结线：

- V1 不补完整第 2 年以后内容。
- 终局系统服务第一年纵切和后续扩展，不强行消耗内容产能。

## 阶段 6：V1 发布准备

**时间：2026-08-15 至 2026-08-31**

目标是把项目整理到可以公开发布的网页版本。

必须交付：

- 静态网页部署流程和发布检查清单。
- 存档版本迁移策略和回归测试。
- 基础错误边界，坏存档恢复提示。
- 首屏加载、移动端触控、字体、布局稳定性检查。
- 玩法说明、版本说明、已知限制。
- 至少一轮手机浏览器和桌面浏览器长测。

验收标准：

- 生产构建可以部署到静态网页托管。
- 新存档、旧存档、坏存档都有明确行为。
- 手机浏览器可以完整游玩至少 30 分钟。
- 桌面浏览器可以完整游玩序章到毕业后第一年。
- 发布包不包含调试入口、测试态按钮或不可解释的占位文案。
- 随机事件体验可重复测试：测试态能固定随机种子，普通游玩能产生差异。

## V2+ 后续年份路线

V1 发布后，后续年份按内容包扩展，不按固定主线一次写完。

### 阶段 7：第 2-3 年起步期内容包

目标是让毕业后的早期沙盒从一年扩到三年。

必须交付：

- 起步期年度结算完善。
- 第 2-3 年随机事件池：Livehouse、兼职压力、Demo 传播、小厂牌接触、外地小演出。
- 第一次正式发行固定保底。
- 起步期稀有事件：地下爆红、关键乐评、成员短暂离开、录音失败。

验收标准：

- 起步期能稳定支撑 24 个月游玩，不明显重复。
- 不同路线能进入地下、商业、低迷三种明显状态。

### 阶段 8：第 4-7 年上升期 / 困住期内容包

目标是让乐队开始分化：上升、困住、转型或破裂。

必须交付：

- 首张专辑或等价大作品周期。
- 合约诱惑、商业妥协、巡演压力、风格转型事件池。
- 成员长期路线：坚持、离开、复归、换人。
- 路线标签：地下传奇倾向、主流成功倾向、实验转型倾向、燃烧透支倾向。

验收标准：

- 第 4-7 年不只是数值膨胀，必须改变事件池和结局倾向。
- 至少 3 条路线能产生明显不同的作品、成员和名声结果。

### 阶段 9：第 8-15 年成熟期 / 危机期内容包

目标是把长期成功和长期代价做出来。

必须交付：

- 巡演、专辑评价、媒体反噬、制作人合作、健康风险事件池。
- 大型特殊剧情：巅峰现场、争议专辑、核心成员摊牌、重大健康事故。
- 长期疲劳和关系债务进入年度结算。
- 成熟期作品和荣誉影响结局权重。

验收标准：

- 玩家可以感受到“成名也有代价”。
- 高名声、高压力、低健康、低关系能自然导向不同危机。

### 阶段 10：第 15 年以后后期生涯内容包

目标是让生涯后期不只是等待结局，而是有退役、复出和转型选择。

必须交付：

- 退役、告别演出、解散重组、转制作人、经典巡演事件池。
- 年龄、健康、名声衰退或沉淀机制。
- 复出和传承类特殊剧情。
- 人生评价扩写，读取完整生涯履历。

验收标准：

- 后期生涯有主动选择，不只是随机死亡或强制结束。
- 终局评价能解释一生的关键作品、成员关系、荣耀和遗憾。

## 技术任务队列

优先级从高到低：

1. 存档迁移：引入 schema migration，支持从 `SAVE_VERSION = 1` 迁移到新增状态结构。
2. 阶段状态：增加 `phase: "campus" | "career"`，避免用月份硬编码阶段。
3. 随机事件抽取器：实现权重、冷却、once、repeatable、稀有度、测试随机源。
4. 事件保底机制：长期缺少演出、录音、成员冲突或发行结果时触发兜底。
5. 内容校验：为事件、行动、反馈、履历建立数据完整性测试。
6. 毕业演出：实现序章关键结算和毕业后资源继承。
7. 录音行动：让 `record` 行动生成真实 `Recording`，并处理失败原因。
8. 发行系统：实现 `Recording -> Release` 的正式动作和结果公式。
9. 成员系统：把成员从关系数值扩展为成员实体。
10. 长期阶段：增加 `careerStage`、年度计数、年度结算和长期事件池入口。
11. 结局入口：用退役、解散、健康崩溃、告别演出触发正式结局。
12. UI 细化：增加作品列表、发行列表、成员状态、履历详情、年度摘要。
13. 发布流程：补部署脚本、错误边界和发布检查清单。

## 测试策略

每阶段固定执行：

- 规则层单元测试：行动、事件抽取、事件保底、录音、发行、结局、存档迁移。
- 随机事件测试：固定随机种子、权重边界、冷却、年度上限、一次性事件不重复。
- 内容校验测试：数据完整性、触发条件、重复 id、缺失反馈、非法权重。
- UI 交互测试：开局、行动、事件选择、下月推进、重开、结局页。
- 构建验证：类型检查和生产构建。

发布前额外执行：

- 新存档完整路线。
- 旧存档迁移路线。
- 坏存档恢复路线。
- 同一出身路线两次开局的随机差异检查。
- 固定随机种子的可复现检查。
- 手机窄屏 30 分钟试玩。
- 桌面宽屏序章到毕业后第一年试玩。

## 风险和应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 随机事件失控 | 玩家错过关键体验或剧情断裂 | 用固定锚点和保底机制兜底 |
| 内容量失控 | 阶段延期，质量不均 | 按事件池分批冻结，先补关键路径，再补分支 |
| 随机重复感强 | 沙盒感下降 | 冷却、年度上限、近期重复惩罚、阶段事件池轮换 |
| 数值平衡不稳定 | 玩家看不到选择后果 | 每阶段保留 3 条基准路线：稳健、透支、冲突 |
| 存档兼容问题 | 发布后旧档失效 | 新字段必须先写迁移和旧档测试 |
| UI 密度过高 | 手机端难玩 | 作品、发行、成员状态、年度摘要分区展示 |
| 终局范围膨胀 | 第一版做不完 | V1 只做第一年内容和长期框架，V2+ 分阶段补后续年份 |
| 真实参考过近 | 版权和识别风险 | 只借结构，不借姓名、外观、完整经历和组合关系 |
