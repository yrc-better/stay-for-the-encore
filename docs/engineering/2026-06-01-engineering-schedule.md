# 乐队模拟器工程排期

## 目的

这份文档把《乐队模拟器》从当前可玩 MVP 推进到可发布网页版本。排期按可验收的版本阶段组织，优先保证核心循环、内容量、存档稳定和发布质量，不追求一次性做完整几十年生涯。

## 当前状态

截至 2026-06-01，项目已经具备：

- Vite + React + TypeScript 网页应用骨架。
- 开局职业选择和乐队命名。
- 月份推进、体力消耗、透支和基础数值系统。
- 个人行动和乐队行动。
- 事件触发、事件选项和行动反馈弹窗。
- 作品草稿、歌曲、排练、录音 Demo 的数据管线。
- 装备栏、成员关系、履历、存档校验。
- 响应式布局，覆盖桌面、平板、手机。
- 结局评估模块存在，但主界面暂不暴露“结局预览”入口。

## 排期假设

- 开发节奏按单人主程 + AI 辅助估算。
- 每个阶段结束都必须保持网页可运行、测试通过、可本地试玩。
- 第一版发布目标是“校园序章 + 毕业后第一年”的可玩纵切，不直接完成几十年全生涯。
- 每阶段可以独立发布内部预览版本。

## 阶段 0：MVP 收口

**时间：2026-06-01 至 2026-06-03**

目标是把当前 MVP 整理成稳定基线。

交付内容：

- 移除调试性质的“结局预览”入口。
- 检查所有按钮、行动、事件反馈是否有明确反馈。
- 给当前 UI 和核心模块补齐最小文档索引。
- 确认本地存档坏档时不会白屏。

验收标准：

- `npm test -- --run` 通过。
- `npm run typecheck` 通过。
- `npm run build` 通过。
- 手机和桌面都能完成开局、行动、事件选择、进入下个月。

## 阶段 1：校园序章可玩化

**时间：2026-06-04 至 2026-06-14**

目标是把毕业前一个月到毕业演出做成完整序章。

交付内容：

- 校园序章按月推进，覆盖毕业前上旬、下旬、毕业演出。
- 每个职业至少 3 个职业专属事件。
- 每个固定成员至少 2 个关系事件。
- 毕业演出结算，根据排练、关系、作品质量、压力生成结果。
- 序章结算写入履历，并影响毕业后开局资源。

建议内容量：

- 通用校园事件：8 至 10 个。
- 职业事件：12 个，四职业各 3 个。
- 成员事件：6 至 9 个。
- 毕业演出结果：4 至 6 种。

验收标准：

- 从新开局到毕业演出至少需要 15 分钟。
- 不同职业能看到不同事件。
- 毕业演出结果能明显反映玩家前期操作。

## 阶段 2：毕业后第一年主循环

**时间：2026-06-15 至 2026-06-30**

目标是完成“毕业后才是主线”的第一年玩法纵切。

交付内容：

- 毕业后状态切换，区分校园阶段和主线阶段。
- Livehouse、地下场景、录音室、唱片合作等机会事件。
- Demo 录制后的发布或投递流程。
- 粉丝、口碑、资金、关系的第一轮长期反馈。
- 成员离队风险和新人加入的基础事件。

建议内容量：

- 毕业后通用事件：15 至 20 个。
- Livehouse / 演出事件：6 至 8 个。
- Demo / 录音 / 合作事件：6 至 8 个。
- 成员变动事件：4 至 6 个。

验收标准：

- 毕业后 12 个月内至少能自然完成一次 Demo 和一次演出。
- 玩家能看到销量、荣誉、合约或人脉作为成果事件出现。
- 成员关系差异能触发实质后果。

## 阶段 3：作品、发行和评价系统

**时间：2026-07-01 至 2026-07-14**

目标是让“创作、排练、录音、发行、评价”形成闭环。

交付内容：

- `Recording` 到 `Release` 的正式生产路径。
- Demo、单曲、EP、专辑的发布规则。
- 销量、专业评价、地下口碑、粉丝增长公式。
- 作品风格标签聚合，并影响事件和称号。
- 履历页展示关键作品和发行成果。

验收标准：

- 玩家可以从 Riff 推进到至少一种 Release。
- 发行结果不是固定值，而是受作品质量、排练、装备、名声、宣传影响。
- 成果数据能被后续结局称号读取。

## 阶段 4：成员剧情和乐队风险

**时间：2026-07-15 至 2026-07-31**

目标是把乐队从数值面板推进到有成员命运的群像模拟。

交付内容：

- 固定成员的人物档案、性格倾向和能力。
- 主唱、贝斯、鼓手的个人支线。
- 创作权冲突、主导权冲突、巡演压力、商业妥协。
- 离队、暂别、复归、新人加入事件。
- 成员关系对排练、演出、录音的实质影响。

验收标准：

- 至少一个成员可以因长期关系和事件选择离队。
- 至少一个新人加入事件能改变乐队能力结构。
- 成员剧情不会只改文本，必须影响数值、履历或后续事件。

## 阶段 5：终局和人生评价

**时间：2026-08-01 至 2026-08-14**

目标是把寿命系统、退役、告别演出和人生评价落地。

交付内容：

- 寿命或年龄推进模型。
- 健康、压力、透支和风险事件对寿命的影响。
- 告别演出、退役、隐居、转制作人、解散复出等终局入口。
- 结局页正式入口，不再是调试预览。
- 职业称号判定和人生传记评价。

验收标准：

- 结局必须由玩家过往操作、荣誉、销量、关系、健康共同决定。
- 至少 8 个职业称号可以自然或通过测试态触发。
- 结局页能解释关键判定依据，而不是只给一个标题。

## 阶段 6：发布准备

**时间：2026-08-15 至 2026-08-31**

目标是把项目整理到可以公开发布的网页版本。

交付内容：

- 构建产物部署流程。
- 存档版本迁移策略。
- 首屏加载、移动端触控、字体和布局稳定性检查。
- 基础错误边界，坏存档恢复提示。
- 发布说明和玩法说明。

验收标准：

- 生产构建可以部署到静态网页托管。
- 新存档、旧存档、坏存档都有明确行为。
- 手机浏览器可以完整游玩至少 30 分钟。
- 桌面浏览器可以完整游玩序章到毕业后第一年。

## 技术任务队列

优先级从高到低：

1. 阶段状态：增加 `phase: "campus" | "career"`，明确校园和主线。
2. 内容数据：扩展事件数据，并建立内容校验测试。
3. 发行系统：实现 `Recording -> Release` 的正式动作。
4. 成员系统：把成员从关系数值扩展为成员实体。
5. 结局入口：用寿命结束、退役、告别演出触发正式结局。
6. 存档迁移：引入 schema version 迁移函数，而不是只做形状校验。
7. UI 细化：增加履历详情、作品列表、发行列表。
8. 发布流程：补部署脚本和发布检查清单。

## 风险

- 内容量风险：事件文本和分支会成为最大工作量，必须按阶段逐步补。
- 数值平衡风险：体力、压力、资金和作品质量需要通过完整路线反复验算。
- 存档兼容风险：每次新增状态字段都要考虑旧存档迁移。
- UI 密度风险：手机端行动多，后续新增列表页时需要避免首屏过载。
- 范围膨胀风险：第一版只做序章和毕业后第一年，不把几十年沙盒一次做完。

## 下一步建议

完成阶段 0 后，优先进入阶段 1：校园序章可玩化。它能最快提升游戏体验，也能验证职业剧情、成员关系、毕业演出和履历系统是否成立。
