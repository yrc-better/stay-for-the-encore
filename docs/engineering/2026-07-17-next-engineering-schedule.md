# 乐队模拟器后续工程排期

日期：2026-07-17  
周期：2026-07-20 至 2026-09-25，共 10 周  
基线版本：v0.1 首个可玩垂直切片

## 1. 排期目标

本阶段的目标不是继续横向增加零散按钮，而是把现有首版扩展成一套能够稳定游玩 90-150 分钟、完整经历二十年生涯并得到合理结局的桌面端版本。

开发顺序固定为：

1. 固化当前工程与存档基线
2. 补齐从小场地到大型舞台的成长链
3. 加入主角设备、商业合作与唱片合约
4. 扩充成员、风格和生涯事件内容
5. 完成二十年结局、长局平衡与发布验收

## 2. 排期假设

- 以一名主开发者配合 AI 辅助开发、测试和内容录入为基准。
- 每周按 5 个有效工作日估算，共约 50 个工程人日。
- 首版继续以桌面浏览器为主，不在本周期内开发移动端专用布局。
- 继续使用纯前端本地存档，不增加账号、服务器和云存档。
- 正式人物头像可以与程序开发并行制作，不阻塞核心玩法开发。
- 每周最后半天用于回归测试、试玩记录和排期调整。

## 4. 十周详细排期

### 第 1 周：工程基线与模块整备

时间：2026-07-20 至 2026-07-24  

主要任务：

- 整理并提交当前从零重写后的干净 v0.1 基线，确认旧实现删除范围。
- 固定 Node 与包管理器版本，保证本地和自动构建使用相同环境。
- 建立持续集成检查：类型检查、测试、构建和差异格式检查。
- 将超大的 `Workstation.tsx` 按页面、弹层和视图模型拆分。
- 将 `OpeningFlow.tsx` 按开局步骤拆分，保留现有行为和测试。
- 统一行动、事件和月末结算使用的游戏状态复制逻辑，避免新增字段漏复制。
- 增加应用级错误边界、构建版本号和基础诊断信息。
- 记录当前 JavaScript、CSS 和首屏资源体积基线。
- 生成一个稳定的本地试玩构建。

验收标准：

- 工作树形成可回滚、可发布的明确基线。
- 页面拆分后现有功能、33 项以上测试和视觉表现不退化。
- 每次提交都可以自动执行类型检查、测试和构建。
- `npm test` 与 `npm run build` 持续通过。

### 第 2 周：存档 v2 与内容数据契约

时间：2026-07-27 至 2026-07-31
版本：v0.1.1

主要任务：

- 为存档增加版本化 envelope、明确的 `saveVersion` 和迁移注册表。
- 实现 v1 至 v2 迁移、升级前备份和迁移失败回退。
- 增加损坏存档提示、清除入口以及存档导入、导出能力。
- 为后续巡演、设备、合约和机会字段建立安全默认值。
- 增加新游戏、手动保存、年度自动保存、刷新恢复和损坏恢复测试。
- 为候选人、事件、场地、风格和行动建立运行时数据校验。
- 检查重复 ID、非法引用、负权重、错误目标和越界数值。
- 统一 `creation/creativity`、`heat/popularity` 等内容层与领域层命名。
- 将风格修正收敛为单一配置来源。
- 输出内容数量和缺失引用报告。

验收标准：

- 新开游戏、手动保存、刷新载入和年度自动保存均可恢复到同一状态。
- 旧版存档能够自动迁移，迁移失败不会覆盖原始数据。
- 未知版本或损坏存档不会静默载入错误状态。
- 重复 ID 或无效内容在开发阶段立即报错。
- 后续新增状态字段必须同时提交 schema、默认值和迁移测试。

### 第 3 周：月初演出机会与二三级场地

时间：2026-08-03 至 2026-08-07

主要任务：

- 新增月初演出邀请状态，每月生成 0-3 个限时机会。
- 邀请在月初生成后写入当月状态，刷新页面或重新载入时不能重新随机。
- 邀请根据综合人气、场地解锁、风格和剧情标签调整权重。
- 邀请记录场地、报酬、AP、有效期限、特殊条件和风险等级。
- 接入二级 Livehouse 和三级中型专场、音乐节小舞台。
- 接入一级至三级自主演出和对应前期投入。
- 将风险提示改为针对具体演出计划计算，而不是使用全局固定提示。
- 月末自动清理过期邀请，并在履历中保留已完成的重要演出。
- 增加结构化演出记录，保存等级、评价、收益和是否属于优秀演出。
- 增加邀请生成可复现测试和各级场地收益测试。

验收标准：

- 人气达到 10 后可以正常获得或自主举办二级场地演出。
- 人气达到 30 且至少发行一张专辑后可以解锁三级场地。
- 同一个月仍然只能执行一次演出行动。
- 自主演出比同级受邀演出风险更高、成本更高、人气收益更高。

### 第 4 周：高级场地、演出里程碑与巡演基础版

时间：2026-08-10 至 2026-08-14  
版本：v0.2

主要任务：

- 增加四级大型音乐节、剧场或体育馆演出。
- 增加五级大型巡演和万人场馆机会。
- 记录三级、四级优秀演出的永久里程碑。
- 完整实现四级和五级场地解锁条件。
- 增加消耗 3 AP、状态下降两级的大型演出和巡演结算。
- 在演出页展示场地成长路线、已达成条件和未达成条件。
- 增加高级邀请权重和人气降低后的邀请收缩规则。
- 补充不同风格、状态和专辑质量对演出结果的测试。

验收标准：

- 玩家可以从一级场地连续成长到五级场地。
- 高级场地不会只靠人气解锁，优秀演出与专辑数量条件必须生效。
- 演出履历可以清楚显示关键现场、评价、收益与里程碑。
- 连续模拟 60 个月时，至少存在一条合理进入三级场地的发展路线。

### 第 5 周：主角设备系统

时间：2026-08-17 至 2026-08-21

主要任务：

- 完成电吉他、效果器和音箱三个设备栏。
- 每类设备实现入门、进阶、专业、顶级四档。
- 实现购买、装备、更换和按原价 50% 出售。
- 购买设备不消耗 AP，但必须检查公共资金。
- 设备只修正主角相关的专辑、演出和训练隐藏判定。
- 不为其他成员增加设备或个人资金。
- 经营页增加设备商店、当前装备、价格和效果说明。
- 事件系统预留设备损失、试用和品牌合作效果。
- 补充设备购买、出售、存档和判定修正测试。

验收标准：

- 三个设备栏均可独立升级和出售。
- 设备不会直接修改成员永久属性。
- 资金不足时不能购买，出售回款和存档恢复正确。
- 同一场演出在相同随机种子下，设备升级可以产生可验证的小幅修正。

### 第 6 周：商业合作与唱片合约

时间：2026-08-24 至 2026-08-28  
版本：v0.3

主要任务：

- 增加品牌宣传、专辑授权、平台推广和定制合作。
- 商业合作作为月初机会出现，接受或拒绝不消耗 AP。
- 增加独立发行、小型厂牌和大型唱片公司三种状态。
- 实现签约金、制作成本折扣、发行回款比例和宣传加成。
- 实现合约发行期限、倒计时、完成和违约结算。
- 大型唱片公司提高高级机会出现率，并增加商业干预事件权重。
- 经营页增加合约卡、期限、权益、义务和预计违约后果。
- 履历记录签约、履约、续约或违约。
- 补充合约跨月、专辑发行分成、到期和旧存档迁移测试。

验收标准：

- 同一时间只能存在一份唱片合约。
- 签约后的制作成本、回款和宣传效果符合规则。
- 未按时发行会正确返还签约金并降低基础人气。
- 玩家可以完整经历独立发行、签约和合约结束三个状态。

### 第 7 周：事件引擎与内容生产工具

时间：2026-08-31 至 2026-09-04

主要任务：

- 为事件增加一次性、可重复、独立冷却和生涯阶段条件。
- 接入成员标签、隐藏剧情标签、资金、团魂、专辑阶段和场地等级条件。
- 增加事件链状态，支持 2-4 节跨月短剧情。
- 增加专辑质量调整、邀请生成、商业机会和设备变化等事件效果。
- 增加放弃当前专辑的入口和对应确认流程。
- 将通用行动追加扩展为与训练、社交、排练、宣传等行动相关的专属结果。
- 为事件数据增加唯一 ID、条件合法性、目标成员和结果权重校验。
- 增加开发环境事件预览器或测试夹具，能够指定月份、成员和标签触发事件。
- 防止短期内重复出现同一事件或互相矛盾的剧情。
- 建立事件内容模板和新增事件检查清单。

验收标准：

- 事件结果仍由可保存随机种子决定。
- 同一条事件链可以跨月推进、暂停和结束。

## 5. 并行工作流

### 5.1 内容工作流

内容编写不应全部堆到第 8 周。第 2 周开始即可按照事件模板持续编写，等第 7 周事件引擎完成后批量接入。

每条事件至少包含：

- 稳定且不可重复的 ID
- 事件池和生涯阶段
- 触发条件和权重
- 2-3 个玩家选择
- 正面、负面或无影响结果
- 数值效果或隐藏标签
- 是否可重复及冷却
- 履历标题和简短摘要

### 5.2 视觉工作流

正式日系动画头像可以从第 1 周开始并行制作：

- 6 个主角头像
- 12 个固定候选人头像
- 每个角色保持独立轮廓、发型、服装和代表色
- 统一半身构图、背景明度和头像裁切比例
- 输出 WebP，并保留更高分辨率源文件

程序侧已经支持正式图片加载和失败回退，第 8 周只负责最终接入与检查。

### 5.3 测试工作流

每个功能必须同时增加三层检查：

1. 领域规则单元测试
2. 状态与存档集成测试
3. 用户可见流程测试

每周固定回归：

```bash
npm test
npm run build
git diff --check
```

## 6. 优先级与延期规则

### P0：必须完成

- 存档版本与迁移
- 干净工程基线与持续集成
- 工作站与开局流程模块拆分
- 内容数据运行时校验
- 五级场地成长链
- 设备系统
- 唱片合约
- 条件化事件与事件链
- 完整二十年结局
- 长局平衡与回归测试

### P1：尽量完成

- 40-50 个事件内容
- 十二名候选人的专属剧情
- 商业合作内容
- 正式人物头像
- 开发专用事件预览和长局模拟工具

### P2：可以延期

- 超过 50 个事件后的额外内容
- 更复杂的多城市巡演地图
- 大量专辑封面
- 特殊动画和演出视觉特效

如果进度落后，延期顺序为：

1. 减少额外专辑封面和视觉特效
2. 将事件目标从 50 个降低到 40 个
3. 将巡演保持为一次大型演出结算，不开发多城市地图
4. 保留小型厂牌与大型唱片公司规则，但减少商业事件数量

存档迁移、成长链、结局和长局平衡不可延期。

## 7. 主要风险

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 二十年数值失控 | 中后期失去选择空间 | 第 2 周固化可复现存档，第 9 周批量模拟 240 个月 |
| 事件内容重复 | 90 分钟后体验单调 | 增加事件独立冷却、一次性标记和至少 40 个事件 |
| 新字段破坏旧存档 | 玩家无法继续游戏 | 所有状态变更必须同时提交 schema、默认值和迁移测试 |
| 合约与专辑互相影响复杂 | 回款或期限结算错误 | 将合约修正集中在单一结算层，禁止 UI 自行计算 |
| 高级场地解锁过快或过慢 | 成长节奏失真 | 保存演出里程碑，使用多种随机种子进行 5 年模拟 |
| 正式头像延期 | 视觉完成度不足 | 保留现有独立占位图，视觉资源不阻塞功能验收 |
| 内容与代码耦合 | 每加事件都要改核心代码 | 第 7 周优先完成数据化条件与效果系统 |

## 8. 每周交付要求

每周结束前必须完成：

- 一份可以启动的试玩构建
- 本周新增功能的自动化测试
- 一次至少 30 分钟的人工试玩
- 更新已知问题列表
- 更新存档版本或确认本周无需迁移
- 记录下一周是否需要调整范围

除第 10 周外，每周允许调整任务顺序，但不能同时推进三个未完成的大系统。一个阶段达到验收标准后，再进入下一阶段。
